*Last updated: July 30, 2026 — Session 190 pt 3 — **Found and fixed the real bug behind Olivia's scheduled Aug 1 subscription showing wrong on refresh: `invoice.payment_succeeded` was silently clobbering 'trialing' back to 'active'.** After the pt 2 button fix deployed, David used the new Feature 2 date picker to schedule Olivia onto the Monthly Subscription starting Aug 1 — but refreshing her Customer panel showed the empty "Assign Plan" form again instead of a "Starts Aug 1" scheduled card. Diagnosed with a temporary read-only debug edge function (`debug-stripe-sub`, deployed then retired/neutralized same session — no delete-function tool available from this environment, so it's a 410-stub now; safe to actually delete via the Supabase dashboard whenever convenient) that queried Stripe directly: **Stripe's live subscription was correctly `trialing`** with `trial_end`/`current_period_end` = Aug 1 07:00 UTC, and there was exactly ONE `customer.subscription.created` event on record, whose payload correctly said `status: "trialing"`. But our `subscriptions` table had `status='active'`. Root cause: `stripe-webhook`'s `invoice.payment_succeeded` handler (pre-dates session 190 — originally written for the past_due→active dunning-recovery case) **unconditionally wrote `status: 'active'` on ANY successful invoice**, with no check for what kind of invoice it was. Stripe auto-generates a $0 "trial-start" invoice the instant a `trial_end` subscription is created and immediately marks it `paid` (nothing was due) — which fires this same `invoice.payment_succeeded` event and, ~0.5s after `customer.subscription.created` correctly wrote `'trialing'`, this handler stomped it back to `'active'`. Customer-facing billing was NOT affected (the pricelist-flip gate added earlier in session 190 correctly stayed on `'Delivery'` since it derives from the created/updated handlers, not this one), but every scheduled subscription's *status* silently reverted to full-active immediately on creation — Reports would show her as a paying subscriber on day zero, and `audit_subscriptions_missing_invoice` would have false-positived on her in ~2 hours (status='active' + no real subscription_invoice transaction, since the $0 trial invoice records `amount_paid=0` and skips the transaction insert). **Fix (`stripe-webhook` v51):** the handler now fetches the subscription's live status from Stripe (`stripe.subscriptions.retrieve` → `mapStripeStatus`) instead of hardcoding `'active'` — correctly leaves a trialing subscription alone while still correctly flipping a real dunning-recovery to `'active'`. **Second, smaller bug found + fixed in the same investigation:** admin's `_confirmOptInCharge` re-rendered the Customer panel immediately after `create-subscription` returned, with no wait for `stripe-webhook` to actually write the `subscriptions` row (which is fully async) — a pure race that produced the "empty Assign Plan form" flash David saw the first time, independent of the status bug above. Fixed in `admin-dashboard/index.html` by adding the same 1500ms wait before re-render that customer-app's `confirmSubscribe` already uses for this identical race. **One-time data fix:** Olivia's `subscriptions` row corrected back to `status='trialing'` to match Stripe truth (root-cause code fix above prevents recurrence — this satisfies the Root-Cause Rule, the DB patch and the code fix are paired). **Lesson banked:** when adding a new subscription status value (`'trialing'`) to an existing state machine, audit EVERY handler that writes `subscriptions.status` — not just the ones the new feature obviously touches. `customer.subscription.created` and `.updated` were updated for trialing awareness in the original session-190 pass; `invoice.payment_succeeded` writes the same column and was missed because on the surface it looks unrelated to a "created" flow.*
